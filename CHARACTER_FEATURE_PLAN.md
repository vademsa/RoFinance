## Product contract

- A personal pixel character reacts to the account owner's real, self-reported salary-cycle records. It never changes financial records or moves real money.
- A dedicated Character Profile contains character selection, private explanations, reward points, wardrobe, cosmetic draws and collection exchanges. Existing account-name/avatar editing remains available.
- Statistics contains a separate Character Leaderboard. Participation defaults to off. Public information is limited to an independently chosen pseudonym, pixel character/cosmetic IDs, composite score and rank.
- Income, expenses, balances, banks, debts, transactions, dates of financial events, financial ratios and private explanations are never returned by the leaderboard API. Private account avatars and email-derived names are not reused.
- Points reflect self-reported bookkeeping, not verified wealth or personal happiness. Characters and cosmetics confer no scoring advantage.

## Stage 1 — deterministic rules and catalogue

1. Define typed allowlists for characters, clothing, hats, shoes, hair, faces, expressions and backpacks.
2. Render these as code-native layered pixel SVG; use a normal readable font for Vietnamese/English text.
3. Mood uses salary-cycle available budgets, logged expenses and elapsed-cycle pacing. Missing/incomplete data is neutral. Transfers are not expenses. Archived spending is accounted for without counting archived balances twice.
4. Composite management score is relative, not based on absolute income: total-budget compliance (60), per-jar compliance (25), remaining buffer (15). Empty/unfunded cycles earn no score or points.
5. Only completed, non-overlapping salary cycles from the enrolment cycle onward are reward-eligible, including the cycle in progress on enrolment. At most one reward entry per cycle-end calendar month. Historical backdate corrections recompute existing entries instead of issuing another reward.
6. Rewards: floor(score / 5) points for eligible closed cycles. One-time 40 welcome points do not affect leaderboard rank. Draw costs 20 points; rarities 70% common, 25% rare, 5% special; the tenth unsuccessful rare/special draw guarantees rare-or-better. Duplicates give 5 exchange fragments; 20 fragments buy an unowned cosmetic.
7. Ranked score is separate from spendable points. If a correction reduces earned points below previously spent points, equipment stays owned, but the points shortfall must be offset by future rewards before further draws.

Acceptance: meaningful tests for scale invariance, missing data, transfers, archived jars, closed-cycle eligibility, overlaps, backdate edits, draw guarantees, duplicate handling and unowned equipment. Worker audit gate before stage 2.

## Stage 2 — server-owned state and privacy

1. Add separate PostgreSQL character profiles, draw idempotency records and public ranking projections; financial JSON remains unchanged.
2. All character routes use the existing web-session/mobile-JWT middleware and derive owner from authentication only.
3. Compute mood and rewards using persisted owner data; reject unknown input keys and out-of-list options.
4. Serialize character operations with the same owner advisory lock as financial saves. Debit, random draw, inventory and idempotency result commit atomically.
5. Reconcile rewards and ranking inside the financial save transaction so backdate changes or deleted snapshots cannot leave stale scores. No client-submitted points, rank or inventory.
6. Support idempotent retry of draws with a request UUID in the JSON body. Use cryptographic server randomness.
7. Opt-out deletes published ranking entries in the same transaction. Read rankings through a whitelist DTO and return no internal owner IDs or financial fields.
8. Private explanation/assessment endpoints only read the authenticated account. Bound history, public page size and request rates.

Acceptance: route/integration tests for owner isolation, invalid options, unowned cosmetics, concurrent/retried draws, reward correction debt, opt-out and explicit public field projection. Worker audit gate before stage 3.
